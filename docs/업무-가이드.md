# 업무 가이드 — 이 하네스에서 내가 할 일

팀원이 읽는 문서입니다. 하네스를 고치는 사람은 [하네스-담당.md](하네스-담당.md)를, 왜 이렇게 만들었는지는 [PHILOSOPHY.md](../PHILOSOPHY.md)를 보세요.

한 줄로 줄이면 이렇습니다. **Claude에게 평소처럼 말하고, 보여 주는 걸 확인하고, 정할 것만 정합니다.** 폴더를 열거나 git을 만질 일은 없습니다.

## 모두에게

### 처음 한 번

1. Claude Code를 설치하고 로그인합니다. (회사 안내대로)
2. Claude Code에서 `/plugin marketplace add <하네스 마켓플레이스 주소>`를 한 번 칩니다. 주소는 하네스 마스터가 알려 줍니다.
3. 자기 역할의 플러그인을 설치합니다. 기획자는 `product`, 서버 개발자는 `dev`, 화면 개발자는 `frontend`, 퍼블리셔는 `ui`, 운영은 `infra`.
4. 아무 폴더에서 Claude Code를 열고 **"처음이야, 기획자야"** 처럼 말합니다. 역할에 맞는 저장소가 내 컴퓨터에 받아지고, 내 메모 폴더가 생깁니다.
5. Claude가 열어 주는 `tokens.txt`에 안내대로 토큰을 붙여 넣고 **"다 넣었어"** 라고 말합니다. 토큰은 대화창에 붙여 넣지 않습니다.
6. 받아진 내 폴더를 Claude Code로 열고 **'신뢰'** 를 누릅니다. 이건 보안 확인이라 사람이 직접 합니다.

여기까지 한 번이면 끝입니다. 이후로는 내 폴더를 열고 말만 하면 됩니다.

### 매일

- 내 폴더를 열면 Claude가 먼저 말합니다. 지난번 이후 바뀐 것, 새로 난 결정, 그 결정에 걸린 내 문서, 들어온 질문. 읽지 않아도 Claude가 알려 줍니다.
- 대화 중에도 누가 무언가를 바꾸면 다음 말에 Claude가 말해 줍니다. "방금 기획에서 정책이 바뀌었어요."
- 할 일이 생각나면 그냥 말합니다. 어디에 어떤 모양으로 남길지는 Claude가 정하고 한 줄로 알려 줍니다.

### 하지 않아도 되는 것

- 파일 받기, 올리기, 번호 매기기, 목차 만들기, 형식 맞추기. 전부 Claude와 자동 장치가 합니다.
- 스킬 이름이나 명령어 외우기. "정책 써 줘"라고 하면 Claude가 알맞은 절차를 꺼냅니다.
- 남의 문서 고치기. 할 말이 있으면 "기획에 물어봐 줘"라고 하면 질문이 그쪽으로 갑니다.

### 막히면

"하네스 담당에게 말해 줘"라고 하면 됩니다. 같은 오류가 세 번 나면 Claude가 스스로 멈추고 보여 줍니다. 급하면 하네스 마스터를 직접 부르세요.

## 기획자

무엇을, 왜 만들지 정하는 사람입니다. 끝까지 챙기는 건 **만들어진 게 기획 의도와 맞는지** 입니다.

### 이렇게 말하면 됩니다

| 하고 싶은 것 | 이렇게 말하면 | 생기는 것 |
|---|---|---|
| 새 규칙을 정했다 | "이탈 정책 써 줘. 4번째 이탈하면 바로 제출되게 하자." | 정책서가 생기고, 빈 곳이 있으면 Claude가 한 가지씩 묻습니다 |
| 규칙을 바꾼다 | "취소 가능 시간을 1시간으로 바꿔 줘" | 개발이 기대는 규칙이면 '검토 중'으로 두고 회의 확정 건으로 올립니다. 오타 수준이면 바로 고칩니다 |
| 개발 쪽 질문에 답한다 | "개발 쪽에서 물어본 거 있어?" → 답을 말한다 | 답이 정책서에 들어가고, 물은 쪽 Claude가 바로 압니다 |
| 회의를 정리한다 | "오늘 기획 회의 녹취야, 정리해 줘" | 회의록과 결정 기록 한 줄씩. 다음 날 모두의 Claude가 압니다 |
| 뭔가 남기고 싶다 | "이거 남겨 줘" | 정책이면 정책서, 정한 것이면 결정 기록, 아직 생각이면 내 메모. Claude가 고르고 어디에 넣었는지 말합니다 |
| 올라온 걸 확인한다 | "올라온 거 봐 줘" → 괜찮으면 **"승인"** | 승인이라고 말한 것만 나갑니다 |
| 용어가 헷갈린다 | "이탈이 정확히 뭐였지?" | 용어집에서 찾아 답합니다. 없으면 정하자고 합니다 |
| 어디까지 됐는지 | "이탈 정책 어떻게 됐어?" "다 됐어?" | 개발 쪽 스펙과 티켓 상태를 보고 말합니다 |

### 기획자의 하루

1. 폴더를 열면 Claude가 말합니다. "어제 개발에서 질문이 하나 왔어요. 제가 정책서 규칙 1을 근거로 답해 뒀는데, 아니면 말씀해 주세요."
2. 맞으면 넘어가고, 아니면 "아니야, ~가 맞아"라고 합니다. 바로잡은 답이 개발 쪽에 갑니다.
3. 정할 게 있으면 정합니다. Claude가 "이건 개발 쪽 스펙이 기대고 있어서 큰 결정이에요"라고 하면 회의 안건으로 올려 둡니다.
4. 새 규칙이나 바뀐 규칙은 말로 정합니다. Claude가 문서로 만들고 어디에 넣었는지 한 줄로 말합니다.

### 기획자가 정하는 것

- 정책서를 확정할지 (회의에서)
- 개발이 물어 온 것 중 문서에 답이 없는 것
- Claude가 "큰 결정"이라고 한 변경을 혼자 정할지, 한 사람 더 볼지, 회의로 갈지

## 개발자 (서버 · 화면 · AI)

정한 것을 실제로 돌아가게 만드는 사람입니다. 끝까지 챙기는 건 **만들어진 게 정한 대로 돌아가는지** 입니다.

### 이렇게 말하면 됩니다

| 하고 싶은 것 | 이렇게 말하면 | 생기는 것 |
|---|---|---|
| 기능을 시작한다 | "이탈 처리 기능 시작하자" | 정책서가 있는지 보고, 없으면 기획에 묻고, 있으면 티켓과 스펙을 만듭니다 |
| 스펙을 쓴다 | "이 정책으로 스펙 써 줘" | 정책서 수용 기준 한 줄마다 구현과 시험이 한 줄씩 붙습니다. 정책서가 아직 초안이면 멈추고 말합니다 |
| 애매한 게 있다 | "정책서에 이게 없는데, 기획에 물어봐 줘" | 기획 폴더에 질문이 올라가고, 답이 오면 Claude가 말합니다. 답 전에는 정책서 범위대로만 만듭니다 |
| 구현 중 정책 빈틈을 발견했다 | "결제 쪽이 배송 준비 중에도 취소를 받네. 정책서엔 없는데." | 사용자에게 보이는 결과가 달라지면 정책 쪽 질문으로 올립니다. 코드에서 정하지 않습니다 |
| 버그 같다 | "버그 같아요. ~했더니 ~됐어요" | 정책 문제인지, 스펙 문제인지, 구현 문제인지 가르고 고칠 곳을 말합니다 |
| 내 상태를 본다 | "지금 내 스펙 상태 어때?" | 기대던 정책이 바뀌어 낡은 스펙, 답 기다리는 질문, 티켓 상태 |
| 올린다 | "올려 줘" | 브랜치·커밋·PR을 Claude가 합니다. 주인이 "승인"하면 들어갑니다 |

### 개발자의 하루

1. 폴더를 열면 Claude가 말합니다. "기획에서 이탈 규칙이 바뀌었어요. 내 스펙 하나가 여기에 걸려요."
2. "바뀐 대목 보여 줘" → 반영할지 정합니다. 정책이 아직 '검토 중'이면 반영을 기다릴 수도 있습니다.
3. 구현하다 정책서가 말하지 않는 걸 만나면 짐작하지 않고 말합니다. Claude가 질문으로 올립니다.
4. 끝나면 "올려 줘". 주인이 승인하면 티켓도 같이 움직입니다.

### 개발자가 정하는 것

- 정책을 어떻게 만들지 (스펙)
- 사용자에게 보이지 않는 구현 세부 (재시도 횟수 같은 것)
- 스펙과 코드를 승인할지

## 하네스 마스터

팀의 일하는 방식을 챙기는 한 사람입니다. 스프린트 마스터처럼요. 팀 전체가 쓰는 규칙·스킬·양식은 하네스 마스터를 거쳐 모두에게 갑니다.

### 처음 세울 때 (Claude Code에서, 이 순서로 말하면 됩니다)

하네스 저장소를 받아 그 폴더를 Claude Code로 열고 나서:

1. **"우리 팀 구조 정하자"** — 역할, 사람 수, 무엇을 만드는지, 누가 승인하는지를 차례로 묻습니다. 표로 보여 주면 보고, 바꿀 게 없으면 **"승인"**. 그러면 팀 구성이 적히고 저장소 골격이 만들어집니다.
2. **"연결 값 넣자. Bitbucket 워크스페이스는 ~, Jira는 ~"** — `remotes.json`에 원격 주소·Jira 주소·마켓플레이스 주소가 들어갑니다. 이미 만들어 둔 Bitbucket 저장소가 있으면 그 주소를 씁니다.
3. **"골격을 Bitbucket 저장소에 올려 줘"** — 만들어진 폴더들이 각 저장소의 첫 커밋으로 올라갑니다. 저장소가 비어 있어야 합니다.
4. **"main 보호 걸어 줘"** — 직접 올리기 금지, 주인 그룹만 승인·머지. Bitbucket 화면에서 직접 해도 됩니다.
5. **"설치 안내 만들어 줘"** — 팀원에게 보낼 마켓플레이스 주소와 "처음이야" 안내 한 장.
6. 팀원 한 명과 같이 **"처음이야"** 부터 첫 승인까지 한 번 해 봅니다. 여기서 막히는 게 곧 고칠 것입니다.

### 운영할 때

- **요청이 오면**: "이런 것도 Claude가 해 주면 좋겠다" → 하네스 저장소에서 스킬이나 규칙을 다듬고 → 버전을 올려 한 번 내보내면 → 모두의 Claude에 자동 반영됩니다. 각자 설치하거나 업데이트할 일은 없습니다.
- **기준**: 팀 전체에 영향을 주는 것만 엄격하게. 혼자 쓰는 요령은 각자 자유롭게.
- **스프린트마다 한 번** 하네스 회의. "그거 어떻게 됐어요?"를 몇 번 물었는지가 지표입니다. 물어야 알았다면 하네스에 빠진 장치가 있는 것입니다.
- **고치는 법**은 [하네스-담당.md](하네스-담당.md). 시험을 돌리고, 시연 환경에서 세 창을 다시 열어 보고, 올립니다.

## 도구마다 맡는 일

| 도구 | 맡는 일 | 기억할 것 |
|---|---|---|
| 저장소(폴더) | 팀이 아는 모든 것. 정책서, 스펙, 결정, 회의록 | 여기 없으면 없는 것 |
| Jira | 일이 어디까지 왔는지. 사람 부르기 | 업무 요청과 진행 상태는 Jira 댓글로. Claude는 상태를 읽고 옮기지만 댓글은 읽지 않습니다 |
| Confluence | 밖에서 들여다보는 창 | 여기에만 쓴 건 저장소로 옮겨야 효력이 생깁니다 |
| Teams | 사람을 부를 때 | Claude는 메신저를 읽지 않습니다 |
| 양식 | 정책서·스펙·질문·결정 기록·회의록의 틀 | 채우는 건 Claude, 사람은 내용만 |

회의나 메신저에서 정한 것도 저장소의 결정 기록에 한 줄 올라가야 모두의 Claude가 압니다. "제가 말씀드렸는데요"는 근거가 되지 않습니다.
